📦 Products Dashboard — Build Guide

How to build a new products dashboard that reads the same Supabase and produces numbers that reconcile with Odoo.

Golden rule: a single wrong number destroys trust in the whole dashboard. Every metric must be reproducible on a named Odoo screen. Never mix bases (orders vs invoices, taxed vs untaxed, raw vs UoM-normalized). When unsure, label the basis in the UI.

1. Architecture

Odoo  →  n8n (sync)  →  Supabase (Postgres + REST)  →  browser dashboard
  • Static, no build. Plain HTML + vanilla JS + Chart.js (CDN). No framework/bundler.
  • The browser reads Supabase REST directly. n8n already keeps the tables fresh — you only read, you don't build syncs.
  • RTL Arabic + English, money in IQD, calendar anchored to Asia/Baghdad.

REST: GET {URL}/rest/v1/{table}?select=...&{filters}  ·  Headers: apikey: <anon> and Authorization: Bearer <JWT>.

⚠️ Auth is required (RLS). The tables have Row-Level Security — the anon key alone returns nothing. Every read needs a logged-in user's JWT. Pagination — Supabase caps responses at 1,000 rows

async function sbGetAll(pathAndQuery, headers) {          // headers include apikey + Bearer JWT
  const PAGE = 1000, sep = pathAndQuery.includes("?") ? "&" : "?";
  const url = o => `${SUPABASE_URL}/rest/v1/${pathAndQuery}${sep}limit=${PAGE}&offset=${o}`;
  const first = await fetch(url(0), { headers: { ...headers, Prefer: "count=exact" } });
  const out = await first.json();
  const total = Number((first.headers.get("content-range") || "").split("/")[1]);
  if (out.length === PAGE && total > PAGE) {
    const offs = []; for (let o = PAGE; o < total; o += PAGE) offs.push(o);
    const more = await Promise.all(offs.map(o => fetch(url(o), { headers }).then(r => r.json())));
    more.forEach(rows => out.push(...rows));
  }
  return out;   // ALWAYS add a unique sort tiebreaker, e.g. &order=line_id.desc
}

4. ⭐ Most important: quantities come from sale.report

dashboard_order_lines.qty is UoM-normalized because the sync sources it from Odoo's sale.report (Sales Analysis), not sale.order.line:

  • sale.order.line.product_uom_qty = raw qty in the line's unit → summing mixes cartons + pieces (garbage; one product summed to 1,061 instead of 303.5).
  • sale.report.product_uom_qty = Odoo's "Qty Ordered" = normalized to the product's reference unit → matches Odoo exactly (303.5 cartons). And sale.report.date is the real order date.

So qty is already correct — do not re-derive it. It's in the product's UoM and can be fractional. sale.report has no order_id and no write_date (it's a view) — hence order_id is null, and the nightly top-up uses a rolling date window.

5. Core conventions (match these or numbers drift)

  1. Confirmed only: state in ('sale','done'). Quotations/cancel never count.
  2. Baghdad calendar: bucket days in Asia/Baghdad, not UTC (week starts Saturday): 
    function bagDay(s){                       // "2026-06-14 20:21:51+00" -> "2026-06-14" (Baghdad)
  if(!s) return "";
  const d = new Date(String(s).includes("T") ? s : String(s).replace(" ","T")+"Z");
  return isNaN(d) ? String(s).slice(0,10) : d.toLocaleDateString("en-CA",{timeZone:"Asia/Baghdad"});
}
  3. Quantity = normalized (from sale.report); never sum raw sale.order.line.
  4. Date = date_order (real order date), bucketed in Baghdad.
  5. Revenue = price_subtotal (untaxed) = Odoo "Untaxed Total". price_total = taxed.
  6. Margin = revenue − cost × qty (gross; cost = standard_price).
  7. Exclude fixtures عارضات و استاندات: filter out category ~ 'عارضات|استاندات'.
  8. Escape DB strings (esc) before innerHTML (names are user-controlled → XSS).
  9. De-dupe by PK; money = IQD compacted to K/M.

7. Verify every number against Odoo

Tool: Sales → Reporting → Sales (Sales Analysis pivot). Always filter Sales Orders; Measure = Qty Ordered (units) / Untaxed Total (revenue) / Margin; exclude fixtures.

⚠️ The #1 trap — the end date. "Order Date is between … and 06/30/2026 00:00:00" drops all of June 30. Always set the end to the next day (07/01/2026) or 23:59:59. (This alone caused a whole "127-unit gap" that was purely a filter mistake.)

-- Supabase = what the page should compute (June)
select p.sku, p.name,
       round(sum(l.qty),1)  as units,
       round(sum(l.price_subtotal)) as revenue,
       round(sum(l.price_subtotal) - sum(l.qty * coalesce(p.cost,0))) as margin
from dashboard_order_lines l
join dashboard_products p on p.product_id = l.product_id
where date(l.date_order at time zone 'Asia/Baghdad') between '2026-06-01' and '2026-06-30'
  and l.state in ('sale','done')
  and coalesce(p.category,'') !~ 'عارضات|استاندات'
group by p.sku, p.name order by units desc;

8. How the data stays fresh (you rely on it)

  • Products + Stock — every 2h from product.product (catalog + qty_available + cost).
  • Order-lines full backfill — one-time, month-chunked from sale.report (after truncate).
  • Order-lines nightly top-up — 02:00, upserts last ~10 days from sale.report. (No write_date → cancellations/old edits are cleared by an occasional full re-backfill.)

9. ⚙️ Recommended architecture for the NEW build

The removed page loaded ~100k raw lines into the browser → slow, and its ~100 paginated requests slowed the whole Supabase project. Do not repeat that. Instead: aggregate server-side — create Postgres RPCs / views returning the summaries the UI needs (frozen list, top products for a window+filters, per-product drill), with filters as parameters. The browser then downloads kilobytes, not megabytes, and stays fast at any history depth.
